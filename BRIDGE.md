# window.host: the page ↔ host contract (phase 3)

The host (`src/bridge.js`) defines `window.host` before the page's own scripts run. A plain browser has no `window.host`; the page then uses its mock data (`web/tools/host-mock.js` imitates this contract).

## Values the host keeps current
| Key | Shape | When it changes |
|---|---|---|
| `covered` | `true` while a maximised or full-screen window covers this screen. The host hides the view right after telling the page, so rendering stops. | on cover / uncover |

Home groups windows of one app into one tile | when the list changes (checked every 0.5 s) |
| `location` | `{ lat, lon, place }`, Oslo for now | once at load |
| `sun` | `{ elevation, at }`, degrees and local ISO time | every 60 s |
| `screen` | `{ index, primary, role, slot, x, y, width, height, hz }`: the monitor this page is on (physical pixels; `index` = place left to right among the screens Tidepool runs on, as Setup › Screens arranges them; `role` = `main` (the menu) \| `partner` (beside it: clock, Winamp, notifications, and the row's tail when it is on the right) \| `extra` (the scene only); `slot` = place from the main screen, -1 = just left of it; `hz` = its refresh rate) | once at load |

| `studio` | same shape, one item per project folder from FL Studio's recent-projects list, in its order. `id` = `flp:<newest .flp>`, `name` = folder, `info` = `{ project: { bpm, fl, channels, patterns, plugins[], created, minutes } or null, folder: "dir:<path>", versions[], renders[], backups[] }`; each of the three lists is `[{ id, name, modified, size }]`, newest first (versions = the folder's .flp files, renders = its .wav/.mp3/.ogg/.flac named after one of those .flp files (FL's export name; other audio there is the project's samples), backups = FL's Backup\ autosaves). `project` is read from the newest .flp itself (Places.Flp). A folder with more than 6 .flp files keeps one item per file | same as `games` |
| `web` | same shape (src/Web.cs). | `tracks` | same shape: every song bounced in FL Studio's projects folder (Documents\Image-Line\FL Studio\Projects, all of it, not only recent projects), one per project folder = its newest render, newest first. `id` = `file:<render>`, `name` = render name, `detail` = folder, `info` = `{ kind: "track", size, project: "flp:<newest .flp>", saved, flp: { bpm, minutes, ... } or null, takes: [{ id, name, modified, size }] }` (takes = the folder's other renders, 8 at most; saved = when the newest .flp was saved). | `nowPlaying` | `{ app, title, artist, album, playing, art, pos, dur, at, canSeek }` or `null`: the Windows media session (what the volume flyout shows; Spotifast here, also browsers). `app` = player in lower case (`spotifast`), `art` = album art as a `data:` url or `null`. `pos` / `dur` in seconds (0 when the player does not say), `at` = when `pos` was true (unix ms): count on from there while `playing`. | `heard` | `[{ app, title, artist, album, at, art }]`, newest first, 200 at most: what the media session played (kept in app/.heard.json). | `spectrum` | `[32 ints 0..255]`: what the PC plays (WASAPI loopback, all sound), 32 log-spaced bands 40 Hz..16 kHz, smoothed, auto gain (src/Spectrum.cs). | `notifications` | `[{ id, app, title, body, at }]`, newest first, up to 20: the toasts in Action Center, read from Windows' own store (`%LOCALAPPDATA%\Microsoft\Windows\Notifications\wpndatabase.db`, read-only; no consent prompt or app identity needed). `id` grows with each new one, `at` = unix s. Windows still shows its own toast; the page only counts and lists them | when the store changes (checked every 2 s) |

## Two monitors
- One WebView2 per monitor, each its own page. The pages do not share memory: sync them from the clock (`Date.now()`) or the sun, not from a frame counter.
- **Solo screen 2:** while windows cover screen 1 (`s1cov` in the relay) or the menu is up on screen 2, screen 2 drops its mirror role (`SOLO`, body class `solo` instead of `dual s2`) and runs the whole desktop itself: rail, row, card, its own place in the menu, idles to the clock. Uncovered, it says hello and screen 1 repeats its state.
- The pause rule is per screen: a maximised window on the second screen pauses only that page (`covered` on that page).
- **Frame rate per screen:** every view lives in one desktop window that spans both monitors, so Chromium paces both to the main screen's 144 Hz. On a slower screen the bridge paces `requestAnimationFrame` to that screen's `hz` (measured: 60 fps on the 60 Hz screen). **CSS animations and transitions are not paced** and still tick at 144 on the second screen, so keep second-screen motion in JS (rAF) or keep its CSS animation light.

## Events
- `addEventListener("host", e => …)` with `e.detail = { type, value }` for every update above, and `type: "live"` when a file in `web/live/` changed (the page re-reads `theme.json` and `live.css` itself; the host does not inject anything).
- `host.on(type, value => …)` does the same for one type.
- The first update after load is the full set (screens, screen, location, sun, windows, covered), sent when the bridge says it is ready.

## The menu (phase 2)
- **Open:** Win+Esc, or `host.openMenu()`. The primary screen's page (or, while windows cover the primary screen and another screen is free, that screen's page, so a full-screen game stays put) leaves the desktop layer and becomes a focused full-screen window, so keyboard, mouse and the Gamepad API (`navigator.getGamepads()`) reach it. The `menu` event says `{ open: true }`; a covered page is shown again while it is the menu.
- **DualSense PS button** toggles the menu (the host reads the pad's HID reports through Raw Input, USB or Bluetooth, also while another app has focus; Sony 054C:0CE6 and the Edge 0DF2). Steam may also react to it if Steam's "Guide button focuses Steam" is on.
- **Close:** Win+Esc again, `host.closeMenu()`, launching something, or the user clicking/alt-tabbing to another window. Focus goes back to the window the user had before (not after a launch).
- **Escape and the pad:** a keyboard `Escape` that the page does not `preventDefault()` closes the menu; the pad's ○ goes back a level but never closes it (PS does). While the menu is open the bridge turns the pad into keydowns (the DualSense is decoded by the host from its HID reports and sent as a `pad` event = the keys held down, because WebView2's Gamepad API does not list it; other pads come through `navigator.getGamepads()`) on `document.activeElement`: ✕ Enter, ○ Escape, □ Delete, △ F2, Create Tab, Options F3, L1/R1 PageUp/PageDown, L2/R2 `[` `]` (cycle the list's sort), D-pad and left stick arrows (repeat after 400 ms, every 110 ms). So one key handler covers both: `preventDefault()` Escape while a submenu can go back a level, let it through at the top level. Pad glyphs on the page are PlayStation symbols drawn by CSS (`.p-A` ✕, `.p-B` ○, `.p-X` □, `.p-Y` △, `.p-G` PS).
- **Mouse while the menu is closed:** left clicks and moves on the bare desktop (no app window under the pointer) reach the page under them as real mouse events (`mousemove`, `mousedown`, `mouseup`, `click`), with the page's own coordinates. Right click and the wheel stay with Explorer.

## The Claude panel (phase 3)
`host.claude` is the user's own Claude Code (`claude -p`, their sign-in, settings, hooks and MCP servers; the host never sees a key) as a
general desktop assistant: every tool, `--permission-mode bypassPermissions` (the panel cannot answer prompts), working in `E:\Projects`,
30-minute limit, `cancel()` stops it. Its system prompt says it is in the desktop's chat panel (replies render as Markdown) and that
`app/web/live/` restyles the desktop. There is no undo (user, 15 Nov: removed after accidental clicks). A freshly loaded page calls `newChat()`, so the panel and Claude's memory start together.
Several chats can work at once: each has its own claude process. The panel shows one; `newChat()` or `resume(id)` while it works leaves it going in the background,
where its events are not sent (only `claude-busy`). A background chat's claude is closed when its ask ends; `resume` starts it again.

## Spotify in Music (`host.spotify`, src/Spotify.cs)
Signed out it reads Spotifast's own cache (`%LOCALAPPDATA%\paolino\spotifast\cache`: library = every playlist, in the user's sidebar order from Spotifast's settings; `playlists\<account>\<id>.rows.*` = songs of the playlists opened in Spotifast; liked-songs = newest 50; home = mixes, recently played, top tracks; `data\history.json` = what Spotifast played, with uris) and plays through `spotifast play-uri` / `play-search`.
`connect()` signs the desktop in once through the user's own Spotify app (Spotifast's `web_client_id`, PKCE, redirect `http://127.0.0.1:8989/login`, which is what Spotifast's guide has users register; the host listens there for 3 minutes). The refresh token is DPAPI-sealed in `app/.spotify` (not in git). Connected, the Web API adds search, adding to playlists, Liked Songs, Play next, all liked songs, and playing a song inside its playlist/album on Spotifast's Connect device. Development Mode rules (Feb 2026): search gives 10 per type; playlist items only for playlists the user owns (others come from the cache); adding is `POST /playlists/{id}/items`, liking `PUT /me/library`.

| Call | Answer (event) |
|---|---|
| `state()` | `sp-state` = `{ connected, user, cache, playlists: [list], mixes: [list], albums: [list] (saved, Web API, refreshed every 30 min or after a save), lately: [list] (albums of what Spotifast played, newest first), liked: { total, items: [song] }, recent: [song], top: [song], artists, history: [song] }`; also sent at load and when the menu opens, if it changed |
| `search(q)` | `sp-search` = `{ q, local, tracks: [song], artists: [{ uri, name, art, followers }], albums: [list], playlists: [list] }` (`local` = signed out, from the cache) |
| `list(uri)` | `sp-list` = `{ uri, items: [song] \| albums: [list], note?, more? }`; uri = a playlist, album, artist or `spotifast:liked-songs` |
| `play(uri, context)` | a song (inside `context` when given), or a whole playlist / album / artist |
| `best(q, kind)` | Spotifast's own `play-search` (signed out) |
| `add(playlistId, uri, name)`, `like(uri, name)`, `queue(uri, name)`, `save(albumUri, name)` | `sp-done` = `{ op, ok, message, id }`; `message` = the song's name, or why not (`"connect"` = sign in first) |
| `now()` | `sp-now` = the playing song as a `song` (Web API, else Spotifast's history) |
| `connect()`, `disconnect()` | `sp-done` op `connect`, then `sp-state` |

`song` = `{ uri, name, artists, artist (first artist's uri), album, albumUri, art, dur }`, `list` = `{ id, uri, name, kind (playlist/album), owner, mine (yours or collaborative: you can add to it), count, art, desc }`. Art urls are Spotify's own https images.
`ConsoleDesktop.exe --spotify <op> [json]` runs one call without the desktop and writes its events to `logs/spotify-test.txt`.

| `list(kind, id, sort?)` | `yt-list` = `{ kind, id, sort, title, channel, channelId, followers, items, error? }`: `channel` (a UC id) = its newest 30 uploads (sort `popular` = YouTube's UULP list, most viewed first; `oldest` = all of UULF reversed, about 4 s per 500; `playlists` / `shorts` / `streams` = those tabs, playlists as `kind: "playlist"` items), `playlist` (a PL id) = its first 100, `mix` (a video id) = YouTube's radio list for it, the player's Up next. `published` comes from YouTube's "3 days ago" (yt-dlp's `approximate_date`): day-exact, not to the minute. About 2 s |
| `feed(ids)` | `yt-feed` = `{ ids, items, failed }`: the newest 12 uploads of each channel id, newest first across all of them (150 at most). One yt-dlp per channel, four at a time. YouTube's channel RSS (`feeds/videos.xml`) answered 404 for every channel when this was built (15 Nov 2026) |
| `pop(v)` | no answer: `{ id, title, video, audio, t, vol, embed, to? }` opens a player window of its own (src/PopOut.cs + web/pop.html), one per video (the same video again comes forward), where the last one was left; `to` = `{ x, y }` of a screen (from `host.screens`) opens it filling that screen. Windows drags, snaps and resizes it; flicked by its title bar toward another screen it goes there; F full screen, S next screen, 1-9 or the screen picker = that screen, T on top (only while floating; filling a screen or full screen it is coverable like the desktop), B / ▭ Page view closes it and sends the page `yt-back` = `{ id, t }` (menu lifted on its screen) to play on in the watch page. |

Why two WebM urls: above 360p YouTube serves picture and sound apart; Chromium seeks WebM through its Cues, but reads YouTube's DASH MP4 from the start up to the seek point. WebView2 has no working native HLS (tested 157), so live streams play in the `youtube-nocookie.com` embed. googlevideo throttles one long range request to about 2x the bitrate: fine for playing, seeking far ahead takes a moment.
`ConsoleDesktop.exe --youtube "<query>"` = a search, the first result's stream, its channel, its mix, a one-channel feed, a sorted search and a channel search to `logs/youtube-test.json` (exit 0 = a stream came back).

## Icons for files, studio and web (`art`)
Every item in `files`, `studio` and `web` has `art`: an icon url `https://icons.local/<file>` or `null`.
Files, projects and apps get the Windows shell icon (what Explorer shows, 128 px PNG with transparency; one per file type, programs and shortcuts their own; an icon that only fills a small part of the canvas is cut to its visible pixels).
Sites get the biggest favicon Firefox stored for that page or its host (PNG, ICO or SVG as stored, often 16–64 px: draw it small or on a plate).
Cached in `app/.icons/` (not in git). Measured: 10/10 files, 50/50 projects, 24/24 sites had an icon that loads.
Shell icons are made on STA threads (the scan, each browse): on pool threads the shell answers E_PENDING for some types.

## File previews (`https://drive-<letter>.local/`)
Every fixed and removable drive is mapped as `https://drive-c.local/...` = `C:\...`, so the page shows pictures, videos and text and plays audio straight from disk (the Studio render player, the Files card).
The mapping does not follow a junction off its drive, which is why the host sends real paths. WebView2 runs with `--autoplay-policy=no-user-gesture-required`: the pad's keys are synthetic, so without it a preview (and motion/sound.js's boot chime, as motion.md part 5 planned) would never play.

## Setup's config (`window.TP_CONFIG`, src/Config.cs ForPage)
Injected before the page's scripts: `{ modules: { games, music, video, studio, web, files, claude, voice }, names: { player, browser, daw, ext, ai },
music: { player, rich }, chat: { provider: "claude-code" | "api" | "none", api, model, models } }`. A module false (switched off in Setup, or
nothing installed for it) leaves the rail. `host.setup()` opens Setup; saving there restarts the desktop. The chat events are the same for
Claude Code and a chat API (`claude-*`); an API chat sends `claude-init` with `api: true`, no tools, one chat at a time.
